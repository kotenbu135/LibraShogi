## 0. いつ出すか（引き金）

**方針（2026-09-21 に変わった）: 総局数 360 万局の自動計測が終わったら v0.2 の作業を始める**
（**ユーザーの決定**「総局数が360万に到達し、自動計測が完了したらv0.2リリース作業を開始します」）。

**頭打ちを待たない。** 2026-09-18 の元の方針は「伸びが頭打ちになったら出す」だったが、
**伸びが続くかぎり永久に出ない作りだった**（同日の見積もりで、今のペースが続けば引き金は 1 週間経っても
鳴らない）。v0.2 は最終版ではなく、サイトのハンデ表を実測し直すための土台でもあるので、
局数で区切ることにした。

**頭打ちの判定は続ける**（下の §0.1〜§0.3）。公開の可否を握る役目ではなくなったが、
買い足す価値があるかの目安として読む。

| 見るもの | 頭打ちの合図 |
|---|---|
| `rating --curve` の点 | 横軸を log2(総局数) にしたとき、**続けて 2 つ以上**の節目が「これまでの傾きの線」より下に落ち、95% 区間が線をまたがない |
| 節目ごとの直接対局 | 前の節目の自分との 2,000 局（2026-09-20 に 1,000 から）で、95% 区間の下限が 0 を下回る（`eval/best.jsonl` の足踏み。`best_stall_alert` の WARNING） |
| 外部計測（40 局。2026-09-21 に形を入れ替え: 40 手目まで Libra 同士、41 手目から 水匠5） | 得点が上がらない。ただし 40 局の幅は ±55 Elo なので、これ単独では決めない |

**1 点だけで決めない。** 点のばらつきは約 21 Elo あり、節目 1 つの下振れは普通に起きる（2026-09-19）。

### 0.1 頭打ちの引き金の効き目（2026-09-20 に計算して確かめた）

引き金を決めたときは「妥当そう」で置いただけだったので、**実データ 13 点のあとに節目を 20 回足す計算**を
条件ごとに 400 回ずつ回して、鳴る・鳴らないを数えた（`fit_recent` の当てはめと
「95% 区間が線をまたがない」をそのまま使い、1 点のばらつきは実測の ±35 Elo）。

| 本当の伸び | 8M 局までに鳴る割合 | 鳴る節目（中央） |
|---|---|---|
| +191 / 2 倍（＝落ちていない） | **3.5%**（誤報） | — |
| +142 / 2 倍（25% 落ちた） | 27% | 560 万局 |
| +95 / 2 倍（半分になった） | **96%** | 480 万局 |
| +0 / 2 倍（完全に止まった） | 100% | 320 万局（1 節目） |

**読み方**: 誤報は 3.5% と低く、**止まった・半分になった**は確実に捕まえる。
弱いのは**「25% だけ落ちた」で、3 回に 2 回は見逃す**。ただし v0.2 を出す判断に効くのは
「1 Elo あたり約 8 円を払う価値がまだあるか」なので、25% の鈍りは判断を大きく変えない。
**この引き金は目的に対しては十分**と判断した。

**節目の置き方を等比（総局数 1.25 倍ごと）に変える案も計算したが、採らない。**
25% の鈍りを捕まえる割合は 27% → 39% に上がるが、誤報も 3.5% → 5.8% に上がり、
鳴る総局数はむしろ遅くなる（560 万 → 684 万局）。

**代わりに自己評価の局数を 1,000 → 2,000 にした**（`config/ls.toml` の `anchor_games`・`best_games`、
2026-09-20）。1 点の幅が ±35 → ±25 Elo に縮み、**25% の鈍りを捕まえる割合が 27% → 51%** に上がる。
誤報は 3.2% と変わらない。余分な対局は節目あたり 2,000 局で、40 万局に対して 0.5%。

### 0.2 いま鳴っていないか（2026-09-21、360 万局）

**鳴っていない。下に外れている点は 1 つも無い。360 万局は線に戻った。**

| 節目 | 目盛り | 目安の線 | ずれ | 判定 |
|---|---|---|---|---|
| 240 万局 | +1,177.1 | +1,200.7 | −23.5 | 95% 区間が線にかかる |
| 280 万局 | +1,205.5 | +1,236.8 | −31.3 | 同 |
| 320 万局 | +1,232.6 | +1,265.4 | −32.8 | 同 |
| **360 万局** | **+1,272.4** | +1,289.7 | **−17.3** | 同（線に近づいた） |

**2026-09-20 に「1 点目」と数えかけた 280 万局の点（当時 −37.5）は、データが増えて条件から外れた。**
節目が 1 つ増えて目盛りが引き直され、その点の対局数も 2,400 → 6,600 に増えて幅が変わったため。
**数えなかった判断は正しかった**（360 万局で線に戻ったので、続けて 2 つの条件は成立しない）。
当時「天井に着いた参照に引き下げられているから数えない」と決めたのは結果的に正しかったが、
**そもそも消えた**。

**参照の自動入れ替えは 320 万局で動いた**（2026-09-20 の直し、#20）。win1m と ckpt_000062426 が外れ、
その節目の archive `ckpt_000281893.pt` が新しい参照になった。**ただし入れ替えは測ったあとに起きるので、
320 万局の点自体はまだ天井の参照で測った点。新しい参照で測る最初の点は 360 万局。**

### 0.3 見ておく数字（2026-09-21、360 万局で決着）

**320 万局の落ち込みは一時的だった。伸びは元の水準に戻っている。**

| 区間 | 2 倍あたり |
|---|---|
| 160 万 → 200 万局 | +207 [+139, +275] |
| 200 万 → 240 万局 | +213 [+131, +297] |
| 240 万 → 280 万局 | +183 [+87, +282] |
| 280 万 → 320 万局 | +118 [+39, +198] |
| **320 万 → 360 万局** | **+218 [+128, +308]** |

**参照の入れ替えが効いた。** 新しい参照 `ckpt_000281893.pt`（280 万局の自分）への得点は **0.615**
（+81.4 Elo [33.1, 132.9]）で、帯 0.2〜0.8 のまん中にある。外した 2 つは 0.835・0.855 で天井に着いており、
**目盛りの最近の点を下へ引いていた**（[docs/decisions.md] 2026-09-21 の参照の自動入れ替え）。

**2026-09-20 からの食い違い（直接対局の鎖 +202 / 2 倍 対 まとめた目盛り +150 / 2 倍）は、鎖の側が
正しかった。** 目盛りが天井の参照に引き下げられていたのが原因で、入れ替え後の `fit_recent` は
**+175.9**（残差 11.7、χ²/df 28.4）。**頭打ちではない**ので、局を買い足す価値はまだある
（1 Elo あたり約 8 円）。

## 1. 重みを固定する

1. ユーザーに、どの節目の重みを v0.2 にするかを確かめる（§8-A）。
2. その step の archive を `~/libra-run/releases/v0.2/` に写す。**チェックポイントは直近 3 つしか残らない**ので、決めた直後に写す（v0.1 でそうした）。

```bash
mkdir -p ~/libra-run/releases/v0.2
cp ~/libra-run/ls/checkpoints/archive/ckpt_<step>.pt ~/libra-run/releases/v0.2/libra-v0.2.pt
# ONNX を書き出す（fp32、opset 17）。書き出し方は libra-net/README.md
bin/libra export --ckpt ~/libra-run/releases/v0.2/libra-v0.2.pt --out ~/libra-run/releases/v0.2/libra-v0.2.onnx
( cd ~/libra-run/releases/v0.2 && sha256sum * > SHA256SUMS )
```

3. **この時点の `main` のコミットを控える**（§6 でタグを打つ先）。重みを固定したコミットを選ぶ理由は decisions.md 2026-09-16。

## 2. 玉配置表（`scale.json`）を作り直す

重みが変われば釣り合う組も変わるので、**版ごとに作り直す**。v0.2 の表は Release の添付にもサイトのハンデ表にもなる。

- まず探索で全組のあたりを付ける（v0.1 は 39 秒。ls を止めなくてよい）:
  `bin/libra-scale build --model ~/libra-run/releases/v0.2/libra-v0.2.pt --sims 1600 --out ~/libra-run/ls/scale/scale-v0.2.json`
- **全組（492 組）を検証対局で作り直す**: `bin/libra-scale seq run --dir ~/libra-run/ls/scale/seq-v0.2 --table ~/libra-run/ls/scale/scale-v0.2.json --notify windows`（手順は libra-scale/README.md の seq）。
  v0.1 は 303,677 局・約 12 時間（クラウドの GPU 1 台を足して）。**この間は ls・lx を止める**（§8-B）。
  終わったら表にする: `bin/libra-scale seq table --dir ~/libra-run/ls/scale/seq-v0.2 --out ~/libra-run/ls/scale/scale-v0.2.1.json`
  できた `scale-v0.2.1.json` が**検証済みの表で、配る表はこれ**。`tools/package_release.sh` は重みの置き場の `scale-v0.2.json` という名前を見るので、写す:
  `cp ~/libra-run/ls/scale/scale-v0.2.1.json ~/libra-run/releases/v0.2/scale-v0.2.json`
  **`bin/libra-scale build` の出力（`~/libra-run/ls/scale/scale-v0.2.json`）を写さない。** あちらは探索だけで付けたあたりで、検証対局の結果が入っていない。
- **借りた GPU を足して短くする**（2026-09-21 のユーザーの依頼）: seq の run を始めてから、台ごとに
  `bin/libra-vast --root ~/libra-run/cloud-scale-<n> start --job scale --scale-dir <seq の run> --worker-id vs<n>`
  （手順と注意は libra-cloud/README.md §玉配置表の全組の検証対局）。v0.1 の実測（手元 200 局/分、借りた GPU 240 局/分・実効 $0.226/h）からの目安:

  | 借りる台数 | かかる時間 | 費用 |
  |---|---|---|
  | 0（手元だけ） | 約 25 時間 | $0 |
  | 1 | 約 11.5 時間 | 約 $2.6 |
  | 2 | 約 7.5 時間 | 約 $3.4 |
  | 4 | 約 4.5 時間 | 約 $4.1 |
  | 6 | 約 3 時間 | 約 $4.2 |

  **費用は台数を増やしてもほとんど増えない**（借りた GPU が打つ 1 局の値段は変わらず、増える台数のぶん手元の遅い GPU に頼らなくなるだけ）。
  準備（1 台あたり 5〜15 分）と打ち切りぶんで 1〜2 割の余裕を見る。
- 上位だけでよいなら `bin/libra-scale build --sims 1600` → `verify --top 48 --games 100`。こちらは **ls・lx を止めずに GPU を共有したまま回す**（decisions.md 2026-09-15）。
- 終わったら `verify.v_hat_minus_w`（検証した組の V̂ と実際の勝率の差）を measurements.md に 1 行書く。標準誤差の 2 倍を超えて 0 から離れていたら学習目標の偏りを疑う（v0.1 は −0.008）。

**ハンデ表（tenbin-shogi-web）はこの表から作る**ので、v0.2 では全組が要る（decisions.md 2026-09-19。v0.1 の表は「まだ弱い」ので当てにしない、というユーザーの指摘）。

## 3. 強さを測る（モデルカードに載せる数値）

| 物差し | コマンド | 何が分かる |
|---|---|---|
| 目盛り（主） | `bin/libra rating --curve` | 記録した全対局を 1 本の Elo に当てはめた値と、局数 2 倍あたりの傾き |
| 最強比・基準比 | 自動計測（`eval/best.jsonl`・`anchor.jsonl`） | 直前の自分に勝てているか |
| 固定の参照 | 自動計測（`eval/reference.jsonl`） | run をまたいで変わらない物差し |
| 外部エンジン | 自動計測（`matches/auto-*.summary.json`）。手で打つなら **docs/runbook.md §7.0 のコマンドをそのまま使う** | 41 手目以降の将棋の強さ。じゃんけんの影響を受けない |
| v0.1 との直接対局 | `bin/libra eval --a <v0.2 の pt> --b ~/libra-run/releases/v0.1/libra-v0.1.pt --games 1000` | **「v0.1 からどれだけ強くなったか」。Release の本文に書く 1 行はこれ** |

**外部計測のコマンドをここに写さない**（2026-09-21 にこの節が古くなっていた）。
形は 2026-09-20 に総取り替えされ（布石は Libra 同士、41 手目から やねうら王＋水匠5）、**正は runbook §7.0**。
この節に書いてあった「Libra は `nodes 400`、相手は 1 手 1 秒」はもう無い条件で、そのまま打つと
過去とも今の自動計測ともつながらない点になる。

モデルカードに外部計測を載せる前に、次の 3 つを `matches/auto-*.summary.json` で確かめる。

1. **打った重みが v0.2 のものか。** `match_use_best = true` なので、打つ重みは「最強比が決めた最強」。
   360 万局の世代が有意に勝てなければ**前の節目の重みで打たれている**。`libra_step` が v0.2 の step と
   違うなら、その step を明記するか、v0.2 の重みで打ち直す。
2. **何局か。** 相手の段（`match_go_opp` のコンマ区切り）を探している回は **1 段 10 局**で、
   得点の 95% 区間が ±200 Elo 以上と広い。**段を探した回の数字は載せない**（「較正中」と書く）。
3. **何を測った数字か。** この形では**布石（1〜40 手目）の強さは測っていない**（両陣とも Libra が作って
   打ち消し合う）。モデルカードには「41 手目以降の将棋の強さ」と書く。

**320 万局の節目には外部計測の記録が無い**（2026-09-21 時点。記録は 280 万局の step 246,009 が最後）。
設定は新しい形が効いていて（`progress` の `auto_cfg` が `match_fuseki=self`・`match_use_best=true`）、
`auto.queue` も `running` も空なので、**総取り替えの回に積まれなかったか失敗したかのどちらか（未確認）**。
**360 万局でも出なければ、モデルカード §5 の外部計測は「未計測」と書いて先に進む**（Release を止めない）。
理由は、v0.2 の強さの主な根拠が `libra rating` の目盛りと v0.1 との直接対局 1,000 局で、
外部計測はそこに足す 1 行だから。

**測る前に手元のプログラムを新しくする**（`cd ~/LibraShogi && git pull` → コンソールの停止 → 起動）。
設定はリポジトリから読まれるがプログラムは手元の写しが動くので、新しい設定の鍵を古いプログラムが黙って無視する。
2026-09-19 にこれで 40 局の計測が丸ごと無効になった（measurements.md 同日）。

## 5. 配布物を作る

```bash
# 1. ONNX Runtime（DirectML 版）を取る（初回だけ）
tools/fetch_onnxruntime.sh win-dml
# 2. Windows 版をクロスビルド（libra-engine/README.md）
cmake -S . -B build-win -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-w64-posix.cmake \
  -DLIBRA_BUILD_PYTHON=OFF -DLIBRA_BUILD_TESTS=OFF -DLIBRA_ORT_DIR=$PWD/third_party/onnxruntime/onnxruntime-win-x64-directml-1.24.4
cmake --build build-win
# 3. zip・単体のファイル・SHA256SUMS を作る（第 3 引数は自己対局の標本の中心の時刻）
tools/package_release.sh v0.2 ~/libra-run/releases/v0.2 '<v0.2 の重みに到達した時刻>'
```

- **2 回続けて作って `SHA256SUMS` が一致することを確かめる。** zip と gzip は日時を固定して詰めてあるので、同じ入力からは同じハッシュになる（decisions.md 2026-09-16）。一致しなければ非決定な要素が混ざっている。
- **作った zip を展開して `libra.exe` を動かす**（`usi` → `isready` → 布石の `go` が通り、`info string … provider dml` が出る）。v0.1 でも毎回やった。
- 自己対局の標本は選別していない（搾取者の布石・リーグの局・Gumbel ノイズの手が混ざる）。data/README.md の表に v0.2 の行を足す。

### 8.1 D を実装するときの注意（2026-09-21 に調べた）

2026-09-16 に「既定を変えない」と決めた理由は **v0.1 で配った exe をタグのコミットと一致させるため**
（decisions.md 2026-09-16）で、作り直す v0.2 には当てはまらない。今の形は、GUI 登録でこの欄に手で
パスを入れないと表が使われず、**入れ忘れても何も言わずに動く**（`engine.cpp:46` が `{"Scale_Table", ""}`）。
一方 `DNN_Model` は `exe_dir() + "/libra.onnx"` を既定にして隣を自動で見る（`engine.cpp:41`）。

**直す場所**: `engine.cpp:18`（`VERSION`、C とあわせて）、`:46`（既定）、`:75`（`option name ... default <empty>`
の申告を `DNN_Model` と同じく実際の既定を出す形に）。文書は `docs/protocol.md` §2・§3・§7 とモデルカード。

**踏みやすいところ 3 つ:**

1. **計測ハーネスには影響しない。** 自己評価も外部計測も `bin/libra-usi`（Python 版エンジン
   `libra_league/usi_engine.py`）を `cwd` ＝ リポジトリのルートで起動している（`cli.py:471`）。
   C++ の exe は使っていないので、既定を変えても計測の玉の置き方は変わらない。
2. **Python 版（`usi_engine.py:44`）は同じにしない。** こちらを隣の `scale.json` を見る形にすると、
   **自己評価と外部計測の玉の置き方が黙って変わる**。しかも `rating.py:55` の `_LIBRA_SIG_SKIP` に
   `Scale_Table` が入っていて（点の名前を作る `_sig` が無視する）、**置き方が変わっても `libra rating` は
   別の点に分けず、同じ点に混ざる**。変えるのは C++ の exe だけにして、既定が違う理由を protocol.md に
   1 行残す。
3. **表が無くても壊れない。** `load_scale` が失敗しても `engine.cpp:265` が `info string` を 1 行出すだけで、
   そのまま探索で置く。ただし表を同梱しない人には `cannot open Scale_Table ...` が毎回出るので、
   **既定のパスでファイルが無いときだけ黙らせる**数行を入れる。オフにしたい人は
   `setoption name Scale_Table value <empty>` で戻せる（`engine.cpp:92` が `<empty>` を空文字にする）。
