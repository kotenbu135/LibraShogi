# エンジンの速さの影響調査（2026-09-17）

**2026-09-24 にリポジトリへ取り込んだ**（それまでは会話の一時置き場にしかなく、docs/v0.3-plan.md §4 で「残っていない」と書いたのは誤り）。本文は当時のまま。§3 の計測プログラムは `tools/bench-cpu-2026-09-17.cpp`。

依頼「エンジンの速さ→影響調査から」への回答。**調査だけで、コード・設定・稼働中のランは何も変えていない。**
数値の出所は LibraShogi のリポジトリの記録（docs/measurements.md、docs/decisions.md、docs/status-2026-09-17.md）と、
このセッションで回した CPU だけの計測（下の §3。GPU は使っていない）。見積もりには「未確認」と書いた。

---

## 0. 結論（先に 4 行）

1. **「1 秒で読む局面の数が相手の約 1/1000」は、条件のせいで実際より悪く見えている値。** 学習と GPU を分け合っている最中の値で、GPU を空けると約 1/270。さらに Libra の 1 局面と相手（水匠5）の 1 局面は中身が違うので、この比で強さの差は測れない。
2. **エンジンの時間は、ほぼ全部がネットの推論**（GPU）。探索の計算（CPU）は全体の **3〜5% 程度**（実測、§3）。だから速くするならネットの推論に手を入れるのが正しい。
3. **fp16 は約 2 倍（幅は 1.6〜2.2 倍、未確認）の見込み。** 手間は小さく、**C++ の変更なしで済む可能性が高い**（書き出しの側だけで完結する、§4）。
4. **ただし「2 倍速い＝どれだけ強い」かは、このプロジェクトでは一度も測っていない**（記録なし）。しかも 9/14 の計測では、読みを 4 倍（96→400 回）にしても穴は埋まらなかった。**先に「読みの回数と強さ」の曲線を測るべき**で、その手順は今のコードのままで回せる（§5）。

## 1. 「1/1000」の中身

| 値 | 条件 | 出所 |
|---|---|---|
| Libra 2,988 節点/秒 | 1 手 1 秒、**学習（ls・lx）と GPU を分け合いながら** | status §2.3（9/14 の外部計測のログ） |
| Libra 8,840 節点/秒 | GPU を空けて、複数葉の同時評価（64）あり、fp32 | measurements 9/14 08:50 |
| 水匠5 側 約 238 万節点/秒 | CPU の探索 | status §2.3 |

- 学習と分け合うと **約 3 分の 1 に落ちる**（9/11 の記録「L-S 稼働中は 10〜22 ms/評価に落ちる」とも合う）。GPU を空けた値で比べると差は **約 270 倍**。
- **節点の意味が違う**。Libra は 1 節点ごとに 1,000 万パラメータのネットを 1 回通す。水匠5 の 1 節点は駒割り中心の軽い評価。数を並べても強さの比較にならない（同じことは AlphaZero と従来型の比較でも言われている）。
- **この差がそのまま弱さの原因、とは言えない。** 9/14 の計測では、両者の読みを 96 回から 400 回（4 倍）に増やしても、搾取者に負ける割合はほとんど変わらなかった（86.3% → 87.5%、誤差の範囲）。穴は読みの量ではなく評価（方策・価値）の側にある、という記録が残っている。

## 2. 今のエンジンの速さ（記録より）

複数葉の同時評価（`DNN_Batch_Size`）は **9/14 に実装済み**で、1 葉ずつの約 20 倍になっている。CLAUDE.md の「残りの主な作業」に残っている「複数葉の同時評価」は**すでに終わっている**（fp16 だけが未実装）。

| 1 回にまとめる葉 | 節点/秒（本将棋 41 手目） | 1 回の推論にかかる時間 |
|---|---|---|
| 1 | 413 | 2.42 ms |
| 8 | 3,167 | 2.53 ms |
| 16 | 5,376 | 2.98 ms |
| 32 | 6,984 | 4.58 ms |
| **64（既定）** | **8,840** | **7.24 ms** |
| 128 | 8,508 | 15.0 ms |

この形から、1 回の推論の時間は「**固定の手間 約 0〜1.6 ms ＋ 1 葉あたり 約 0.09〜0.12 ms**」と読める（16〜64 葉と 64〜128 葉に直線を当てはめた値。幅はその 2 本の差、未確認）。
比較: 学習側（PyTorch・fp16・torch.compile ＋ CUDA Graphs）は同じネットのバッチ 64 を **2.16 ms**（1 葉 0.034 ms）で通している（measurements 9/17 11:18）。
**つまりエンジン（ONNX Runtime・fp32）は、学習側と同じ GPU・同じネットで、1 葉あたり約 3 倍の時間をかけている。**

## 3. 探索（CPU）はどれだけ食っているか — このセッションで実測

エンジンの探索ループ（`collect_batch` → 推論 → `apply_batch`）から**推論だけを偽物（即座に返す）に置き換えた**計測プログラムを書き、CPU の時間だけを測った。
条件: このセッションの計算機（Intel Xeon 2.10 GHz・4 コア。手元の Ryzen 9 9950X3D よりかなり遅い）、`-O3 -DNDEBUG`、1 本の木、`Mate_Nodes` 2000、12,800 回読み × 5 回。

| 局面 | スレッド | 1 回（64 葉）の CPU 時間 | 1 葉あたり |
|---|---|---|---|
| 本将棋（41 手目） | 1 / 2 / 4 | 0.18 / 0.18 / 0.19 ms | 約 2.8 µs |
| 布石（2 手目） | 4 | 0.36 ms | 約 5.7 µs |

- **エンジンが 1 回の推論に使う 7.24 ms のうち、探索の CPU は 0.2〜0.4 ms（3〜5%）。** 手元の CPU はこれより速いので、実際の割合はさらに小さい。
- 妥当性の確認: 1 回に集まった葉の平均は 63.4（上限 64）で、手元の記録の 59.3 と近い。1 葉あたり 2.8 µs も、手元の 9/16 の計測（4 スレッド collect＋apply 1.42 ms / 512 葉 ≈ 2.8 µs）と一致する。
- **スレッドを増やしても CPU 側は速くならない**（1 本の木なので）。`Threads` を上げる価値は無い。詰み探索（`Mate_Nodes` 2000）の負担も見えない範囲。
- 限界（未確認）: 偽のネットは方策が一様なので、木の形は本物と少し違う。CPU の絶対値はこの計算機のもの。

**結論: エンジンを速くする余地はネットの推論にしか無い。**

## 4. fp16 でどれくらい速くなるか、どこに手を入れるか

### 見込み（未確認）

固定の手間を 1.0〜1.6 ms、fp16 の 1 葉あたりを 0.045 ms（学習側の 0.034 ms より少し悪く見る）として:

| 1 回にまとめる葉 | 今（fp32） | fp16 の見込み | 倍率 |
|---|---|---|---|
| 64 | 8,840 節点/秒 | 14,300〜16,500 | ×1.6〜1.9 |
| 128 | 8,508 | 17,400〜18,900 | ×2.0〜2.2 |
| 256 | （未計測） | 19,400〜20,500 | ×2.2〜2.3 |

- **約 2 倍**が中心の見込み。固定の手間（入出力の受け渡し）も削れれば、さらに上がる余地がある（最大 3 倍前後、未確認）。
- 葉をまとめる数を増やすと、同時に評価待ちの枝が増えて**読みの質は少し落ちる**（同じ節点数なら弱くなりうる）。64 → 256 は速さだけ見て決めない方がよい。

### 手を入れる場所

| # | 場所 | 内容 | 手間 |
|---|---|---|---|
| 1 | `libra-net/libra_net/export_onnx.py` | fp16 の ONNX を書き出す。**入口と出口は fp32 のままにして中だけ fp16 にすれば、C++ 側は 1 行も変えずに動く**（PyTorch の書き出しで包む形。新しい依存も不要） | 小（半日） |
| 2 | `libra-league/libra_league/cli.py` の `export` / `[auto]` | 対局用に fp16 版も書き出す（`latest-fp16.onnx`）。どちらを使うかの選択 | 小 |
| 3 | テスト（`libra-net/tests/test_export.py`） | fp32 版との出力の差（許容幅）と、形が同じことの確認 | 小 |
| 4 | 文書（decisions / measurements / protocol） | 決定 1 行と実測 1 行 | 小 |
| 5 | （任意）`libra-engine/src/ort_infer.cpp` | 入出力も fp16 にして受け渡しを減らす、置き場所を固定する（IO binding） | 中。1 の結果を見てから |

**注意点**

- **Windows の配布版（desktop）には効かない見込み。** 配布している `libra.exe` は CPU 版の onnxruntime を使う形で、CPU では fp16 に利点が無い（むしろ遅くなる）。9/14 の決定にも同じ判断が書いてある。**fp32 版と fp16 版の 2 つを持つ**ことになる。
- **サイト（tenbin-shogi-web）にも効かない見込み。** ブラウザは onnxruntime-web の wasm（CPU）なので同じ理由。ただし**ファイルは半分（約 20 MB → 約 10 MB）**になるので、読み込みの速さには効く（速さへの影響は未確認）。
- 精度の心配は小さい。**自己対局はすでに fp16 でこのネットを動かしている**（`infer_dtype = "float16"`）。注意の重み付けも学習した有限の値で、fp16 で壊れやすい形（−∞ の遮蔽）は使っていない。

## 5. 「読みの回数と強さ」の測り方（先にこれを測るべき）

**現状: このプロジェクトには、同じ重みで読みの回数だけを変えて強さを比べた記録が無い**（`docs/measurements.md` を全部見た結果。「記録なし」）。
一般には「読みを 2 倍にすると +50〜100 Elo」と言われるが、**Libra で成り立つ保証は無い**。むしろ、
9/17 の調査（status §10）で「価値の予測が学習に使った範囲の外ではほとんど当たらない」ことが分かっているので、**読みを増やしても効きが小さい可能性がある**（読みは価値の予測を頼りに深めるため）。
これを測らずに速くしても、得られた速さが強さに化けるかは分からない。

### 測り方 A（今のコードのまま回せる。C++ も Python も変更なし）

USI の対局ハーネスで、**同じ重みの Libra 同士を、読みの回数だけ変えて**打たせる。`go` に何も付けなければ、各エンジンは自分の `Sims_*` の設定で読む。

```
bin/libra match --games 200 --go "" \
  --opponent "bin/libra-usi" --opponent-cwd <LibraShogi のパス> \
  --libra-opt Sims_Normal=96  --libra-opt Sims_Fuseki=96 \
  --opponent-opt Sims_Normal=192 --opponent-opt Sims_Fuseki=192
```

96 対 192、96 対 384、96 対 1536 の 3 本で「2 倍ごとに何 Elo」が出る。**未確認**: この組み合わせでの実行はこのセッションでは試していない（GPU と重みが無いため）。
時間の見積もり: 1 局あたり数秒、200 局で 30 分前後（GPU を空けた場合。学習と分け合うと 2〜3 倍、いずれも未確認）。

### 測り方 B（速いが、小さな実装が要る）

`libra eval`（同時 64 局で GPU をまとめて使う。1,000 局が約 10 分）は、**今は左右の読みの回数を別にできない**（探索の設定が対局ごとに 1 つしかないため）。
`SearchConfig` に「後手側の読みの回数」を 1 つ足し、手番と枠から選ぶようにすれば使える。**変更は C++ 1 か所＋橋渡し＋CLI で、半日ほどの見込み**（未確認）。

## 6. 効果と手間の一覧（すすめる順）

| 順 | 作業 | 効果 | 手間 | 要る条件 |
|---|---|---|---|---|
| 1 | **読みの回数と強さの曲線**（§5 の A） | 速さの投資が強さに化けるかが初めて分かる。「未確認」がひとつ減る | 小（回すだけ・半日） | GPU を空ける＝ ls・lx の停止（ユーザーの操作） |
| 2 | **fp16 の ONNX**（§4 の 1〜4） | 対局時の読みが約 2 倍（未確認）。学習の速さには影響しない | 小（1 日） | 1 の結果を見てからでよい |
| 3 | 推論の受け渡しの見直し（§4 の 5） | さらに数割（未確認） | 中 | 2 の実測後 |
| 4 | 学習と対局で GPU を分け合わないようにする（計測の間だけ止める、など） | 外部計測の読みが今の約 3 倍に戻る。**コードの変更なし** | ほぼ無し（運用） | 運用の決めごと |

**強さへの効きだけで見ると、この 4 つはいずれも「本体の一般化の問題」より小さい見込み**（9/17 の窓の実験は 13 分の学習で +297 Elo）。
エンジンの速さが効くのは、外部との対局・サイト・デスクトップでの**対局のとき**であって、学習の速さ（局/日）は 1 つも変わらない（自己対局はすでに fp16 で動いている）。

## 7. このセッションで確かめていないこと

- fp16 の実際の速さ（GPU が無いので測れない）。§4 の表はすべて見積もり。
- §5 の A の実行（重みと GPU が無い）。コマンドは読み取りで組んだもので、動作は未確認。
- 手元の CPU での探索の CPU 時間（このセッションの計算機で代用した）。
- Windows 版・ブラウザ版で fp16 が遅くなること自体（一般的な理由からの推測）。
