# Libra — 天秤将棋 最強AI 開発計画書

- 対象ルール: https://tenbinshogi.com/rules/ （天秤将棋）
- 前提: ゼロから開発し、既存の将棋AI実装は参照・流用しない／GPU は vast.ai／成果物・ツール・データはすべて GitHub パブリックリポジトリで公開
- 作成日: 2026-09-11

## 0. 骨子

1. ゲームは「玉配置＋選択（1〜2手目）」「布石（3〜40手目）」「本将棋（41手目〜）」の3層だが、**学習は分離せず、単一ネット・単一自己対局ループで統合**する。分離学習は分布ずれと、学習済み価値関数への過剰最適化を招く。
2. 布石は「打ち手だけの将棋」なので、着手符号化は本将棋の打ち手と同一（玉打ちを1種足すだけ）。専用ヘッドは不要。探索は順序非依存性を活かした**グラフ探索（MCGS）＋Gumbel**。
3. 布石終盤（37〜40手目）と41手目は**厳密に解ける戦術問題**（配置詰み）。証明探索で完全解決し、ネットの近似に任せない。
4. 玉配置の表は「3手目局面の価値ヘッド」そのもの。総当たり対局ではなく、**剪定→深い探索値→バンディット配分の検証対局**で作る。
5. 「最強」は Elo だけでなく**搾取耐性**で定義する。相手が布石の半分を支配できるゲームなので、リーグ学習（搾取者エージェント）を必須にする。

モジュール名（リポジトリ内のディレクトリに対応）:

| モジュール | 役割 |
|---|---|
| `libra-sim` | ルール完全準拠シミュレータ（C++/CUDA、Python バインディング付き） |
| `libra-net` | ネットワーク定義・学習 |
| `libra-search` | MCGS／df-pn／配置詰み証明探索、USI 拡張エンジン |
| `libra-league` | 自己対局・リーグ・評価ハーネス |
| `libra-scale` | 玉配置表（天秤）の生成・検証 |
| `libra-cloud` | vast.ai オーケストレーション、費用モデル |

## 1. ルールから導かれる設計上の事実

**(a) 布石は集合であり、順序に依存しない。** 状態は盤面だけで決まり（未配置の駒は盤から逆算できる）、同一盤面へ至る手順は膨大。Zobrist ハッシュで合流させ、木ではなく DAG で探索・学習する。

**(b) 布石中に相手玉へ届く利きは、飛・香（筋）、角（斜め）、桂（段跳び）だけ。** 五段目は誰も置けないので、**後手玉が四段目にあると飛・香・桂の利きは遮る場所が存在せず**、先手がそれらを1枚でも温存していれば39手目に当てて41手目の裁定で勝ちになる。よって後手玉の実質候補は三段以内（27マス）。三段目でも「飛筋＋角筋」の二本当ては一枚で遮れないので即死しうる。一方、先手玉は41手目に動ける（五段目へ逃げる・駒を五段目へ進めて遮る）ので、同じ利きでも「普通の王手」で済む。この**先後非対称**が布石終盤の戦術と、玉配置表の形（最前段が大損）を決めている。

**(c) 40手目の合法手集合は文脈依存。** 遮る手のみ合法で、遮るべきマスに打てる駒が二歩や筋埋め禁止で無ければ即敗。「合法手ゼロ＝終局」まで含めてシミュレータで厳密化する。

**(d) 41手目は持ち駒ゼロの本将棋だが、玉が自由配置なので入玉・千日手の規定が勝率と釣り合い点を動かす。** 開発前に確定すべきルール: 千日手（四回同一・連続王手の扱い）、入玉宣言（27点法か、無しか）、最大手数。これはルール設計者の決定事項であり、`libra-sim` の設定ファイルとして明文化・公開する。

## 2. 先行研究と部品の対応

| 部品 | 先行研究 | 本件への適用 |
|---|---|---|
| 変則初期局面からのゼロ学習・先手有利の測定 | AlphaZero（Silver+ 2018）、Tomašev+ 2020「Assessing Game Balance with AlphaZero」、Lc0 の Chess960 | 後者は変則チェス群をゼロから学習し先手勝率・引き分け率を測った「釣り合い測定」の直接の先例 |
| 学習効率 | KataGo（Wu 2019）: playout cap randomization、補助ターゲット、局面分岐／Gumbel AlphaZero（Danihelka+ 2022）／MuZero Reanalyze（Schrittwieser+ 2021） | Gumbel は少数シミュレーションで方策改善を保証し、合法手250前後の布石に向く |
| 置換合流 | Monte-Carlo Graph Search for AlphaZero（Czech+ 2021） | 布石 DAG 探索の基盤 |
| 詰み | df-pn（Nagai 2002） | 本将棋の詰み探索と、布石終盤の「配置詰み」証明探索 |
| ネット規模 | Jones 2021「Scaling Scaling Laws with Board Games」、Ruoss+ 2024（探索なし大規模 Transformer）、Lc0 の Transformer 系 | 規模は計算量に対して段階的に拡大 |
| 先後選択 | Hex の swap（MoHex: Arneson+ 2010）、Gomoku の Swap2 対応ボットの開局表、cut-and-choose の部分ゲーム完全均衡 | 選択を「表引き」に落とす根拠 |
| 搾取耐性 | Wang+ 2023「Adversarial Policies Beat Superhuman Go AIs」、AlphaStar リーグ（Vinyals+ 2019） | 自己対局分布外の穴を搾取者で埋める |
| 検証対局の配分 | Best-arm identification（Audibert, Bubeck & Munos 2010） | 玉配置表を効率的に確定 |
| 自陣自由配置 | Arimaa: Wu 2015「Designing a Winning Arimaa Program」、Cox 2006 | Arimaa では配置を少数の定型に固定するのが主流で、配置最適化の知見は薄い。参照価値は限定的 |

## 3. システム構成

### 3.1 `libra-sim` — シミュレータ（C++/CUDA、ビットボード）

- 81マス bitboard、PEXT で飛・角・香の利き生成。
- 布石: 自陣四段マスク、二歩、筋埋め禁止（筋の自陣4マスを歩以外の自駒で埋める手）、玉打ち。
- 40手目: 後手玉への利き集合→遮断マス∩合法打ち場所で合法手を絞る。39手目直後に「遮断不能」を判定して終局（先手勝ち）。
- 41手目: 通常将棋で合法手なし＝先手の負け。以降、打ち歩詰め・千日手・入玉・最大手数。
- 布石中は着手順に非依存な Zobrist キー。1↔9筋の鏡映で正規化した局面キーも持つ（学習データの重複除去と2倍増強）。
- 厳密性テストは必須: 合法手生成の perft、40手目制限の網羅テスト、裁定のエッジケース。テストケース自体もリポジトリで公開し、後続の実装者が同じテストで準拠を確認できるようにする。
- 出力形式: 布石中は持ち駒に玉を含む拡張 SFEN、41手目以降は標準 SFEN。棋譜は USI の打ち手列＋ `choose:sente|gote` トークン。

### 3.2 `libra-net` — 単一・フェーズ条件付き Transformer

- 入力: 81マストークン（駒種・所有・利き数・ピン）＋グローバルトークン（持ち駒／未配置駒の枚数、手番、手数、フェーズ、千日手回数、入玉点数）。
- 幹: エンコーダ 20〜40層、d=768〜1536、2D 相対位置バイアス。30M→100M→300M→1B と段階拡大し、小ネットの自己対局で大ネットを蒸留してから継続学習。
- ヘッド: 方策（本将棋の指し手＋打ち手。打ち手は8種×81で玉を含む）、価値 WDL、補助として (i) 布石局面から41手目局面の探索値 V̂41 を予測、(ii) k手後の駒損得・生存、(iii) 相手の次手予測、(iv) 布石中の「後手玉に当たる利き本数・遮断可否」。
- 鏡映で 2× augmentation。

### 3.3 `libra-search` — 探索

- 共通: PUCT＋Gumbel ルート（Sequential Halving）、バッチ推論、仮想損失。
- 布石: MCGS。合法手は最大7種×36マス程度。
- 布石終盤（35手目〜）: 「配置詰み」証明探索。関係するのは飛角香桂の残数、玉への線・跳びマス、遮断マスだけなので状態空間は小さく、df-pn で完全解決できる。「41手目に先手の応手なし」も同様に証明探索。これらを探索中の終端値に使う。
- 本将棋: MCTS＋df-pn 詰み探索（自玉・敵玉）を並走。
- 対局時: 分散 MCGS（ルート並列＋木並列）、ポンダー。
- 推論バックエンド: TensorRT（最速）と ONNX Runtime（配布しやすい）の両対応。

## 4. 学習パイプライン

### 4.1 統合自己対局

- 各局は**3手目から開始**し、両玉は「ペアサンプラー」が与える。1〜2手目と選択は探索対象にしない（§5）。ネットは先後固定の局面しか見ないので、swap に伴う視点変換が不要になる。
- ペアサンプラーの混合: 全1,296一様（網羅。選ぶ側が悪い配置も評価できるため）／現ネットの価値が0.5に近いペアの重点／搾取者が提案するペア。
- 価値ターゲット: 布石局面は λ·z＋(1−λ)·V̂41 で分散を下げる。本将棋局面は z。
- KataGo 流に playout cap randomization、41手目局面から本将棋を複数回分岐（同一布石の勝率推定を安定化）、Reanalyze。
- ラダー: 小ネットで 10^8 局 → 中ネット → 大ネットへ蒸留＋継続。

### 4.2 `libra-league` — リーグ（搾取耐性）

Main agent、Main exploiter（凍結した本体を相手に布石から学習し弱点配置を探す）、League exploiter（過去全世代を相手にする）、PFSP で対戦相手を選ぶ。

理由: Wang+ 2023 が示した通り、AlphaZero 系の価値関数には自己対局分布の外に穴がある。囲碁では相手が穴へ誘導するのに苦労するが、本ゲームは相手が布石の半分を決められるため誘導が容易。搾取者が見つけた布石を本体の学習分布に混ぜて穴を埋める。収束判定は「ゼロから学習した搾取者の対本体勝率が一定以下で頭打ちになること」。

### 4.3 指標

世代間 Elo、探索値と実勝率の較正、**玉配置表の世代間安定性**（釣り合い集合が動き続ける間は価値関数が未収束）、搾取者勝率。すべて `libra-league` の評価ハーネスとして公開し、後続開発者が同じ物差しで比較できるようにする。

## 5. `libra-scale` — 天秤層（1〜2手目＋選択）の解法

理論: 置く人の利得は min over pairs of max(V, 1−V)。選ぶ人は配置を見てから選ぶので混合戦略は値を変えず、混合は研究外し・予測不能化のためだけに使う。

1. **剪定**: ルール由来の即死ペア（後手玉四段目など）を除外。36×27=972通り、鏡映で約490通り。
2. **探索値**: 各ペアの3手目局面で深い MCGS（10^7〜10^8 ノード）→ V̂。
3. **検証対局**: |V̂−0.5| が小さい上位100ペア程度に限定し、best-arm identification（逐次棄却／トンプソン）で局数を配分。1ペア 10^4〜10^5 局で ±0.5〜0.15%。これ以上の精度は AI 自身の系統誤差より小さく、意味がない。
4. **運用**: 置く側は「信頼区間が最小値と重なるペア集合」から一様サンプル。選ぶ側は V̂≥0.5 なら先手。

V̂ は「この AI 同士の勝率」であり理論値ではない。表は世代ごとに作り直す（探索値は安価、検証対局は最終世代のみ）。表は JSON で公開し、生成スクリプトと検証対局の棋譜も添える。

任意拡張（Nash 保証を捨てる罠配置）: 相手が弱いと分かっているなら、|V−0.5| がほぼ最小の中から「浅い読みでは反対側が有利に見える」ペア（本体と弱いネットの評価差が最大のもの）を選ぶ。別モードとして持つ。

## 6. `libra-cloud` — vast.ai での計算資源設計と費用試算

### 6.1 vast.ai の性質と役割分担

vast.ai は独立ホストのマーケットプレイスで、価格は需給で決まり、ホストごとに信頼性・回線が異なる。ホスト間に高速インターコネクトは期待できない。したがって:

| 役割 | 使うもの | 理由 |
|---|---|---|
| 自己対局・リーグ・検証対局 | 割込可能（interruptible）の RTX 5090／4090、verified ホスト | 完全並列・耐障害。性能単価が最良 |
| 学習 | on-demand の 8×H100 SXM（NVLink）1ノード | 1B パラメータまで単一ノードで足りる。ノード間通信を避ける |
| 玉配置表の深い探索 | 割込可能 H100／5090 | 局面ごとに独立 |
| コーディネータ・リプレイバッファ・重み配布 | vast.ai の外（VPS＋オブジェクトストレージ。Cloudflare R2 など egress 無料のもの） | ホスト障害と切り離す。重み配布の転送量が大きい |

運用ルール: ワーカーは無状態（起動時に最新重みを取得、100局単位で棋譜をアップロード）。プリエンプト時は自動再入札。ホスト検索は verified・reliability 0.98 以上・下り 200 Mbps 以上でフィルタ。Docker イメージは GHCR に公開し、vast.ai のテンプレートとしてリポジトリに置く。

### 6.2 単価の前提（2026年9月上旬、verified ホストの観測値）

| GPU | 割込可能の最安 | on-demand の最安 | 試算に使う計画単価（割込可能、数百〜千枚規模を継続確保する前提） |
|---|---|---|---|
| RTX 4090 | $0.17/h | $0.32/h | $0.25〜0.35/h |
| RTX 5090 | $0.18/h | $0.36/h | $0.35〜0.45/h |
| H100 SXM | $0.67/h | $1.73〜2.21/h | 割込可能 $1.2〜1.8/h、学習用 on-demand $2.2/h |

最安値は単一リストの値であり、まとめて借りると供給を食って単価は上がる。試算は最安値ではなく計画単価で行う。

### 6.3 計算量モデル（後続開発者が再計算できるよう明示）

- 1局面の推論 FLOP ≈ 2 × パラメータ数 × 90トークン × 1.15（attention 等の上乗せ）
- 1局 ≈ 150手（布石38＋本将棋約112）× 平均200シミュレーション ＝ 3.0×10^4 推論
- リーグ・評価・Reanalyze の上乗せ ×1.35
- 実効スループット（バッチ推論、TensorRT）: 4090 8×10^13、5090 1.4×10^14、H100 4×10^14 FLOP/s
- 学習 FLOP ≈ 6 × パラメータ数 × 90 × 1.15 × 局面数 × 3パス、H100 実効 5×10^14 FLOP/s
- 検証対局: 100ペア × 2×10^4 局 × 150手 × 800シミュレーション（300M ネット）

計算スクリプト `libra-cloud/cost_model.py` として公開する。

### 6.4 段階別試算（自己対局分。上乗せ×1.35 込み、余裕率なし）

| 段階 | ネット規模 × 局数 | 自己対局 FLOP | 5090 GPU時間 | 5090 費用 | H100（割込）費用 |
|---|---|---|---|---|---|
| S 検証 | 30M×2×10^7 | 5.0×10^21 | 1.0万 | $3,500〜4,500 | $4,200〜6,300 |
| A 最小実用 | 30M×5×10^7 ＋ 100M×5×10^7 | 5.5×10^22 | 10.8万 | $3.8万〜4.9万 | $4.5万〜6.8万 |
| B 推奨 | A ＋ 300M×10^8（各段階10^8局） | 3.6×10^23 | 71.5万 | $25万〜32万 | $30万〜45万 |
| C 上限 | B ＋ 1B×3×10^8 | 2.9×10^24 | 571万 | $200万〜257万 | $240万〜360万 |

| 項目 | S | A | B | C |

### 6.6 総額と所要時間（プリエンプション・稼働率・試行錯誤の余裕率 ×1.3 を掛けた目安）

| 段階 | 総額の目安 | 自己対局の純計算時間（5090 を1,500枚同時確保した場合） | 現実的な期間 |
|---|---|---|---|
| S | $6,000〜9,000 | 1日未満 | 2〜3週間（開発込み） |
| A | $6万〜9万 | 3日 | 1〜1.5か月 |
| B | $37万〜62万 | 20日 | 2〜3か月（反復回数が律速） |
| C | $300万〜480万 | 160日 | 6か月以上。5090 だけでは足りず H100/B200 を混ぜる |

vast.ai で同時に確保できる消費者向け GPU は数百〜2,000枚程度と見込む。B までは 5090 中心で成立し、C は供給側の制約が予算より先に効く。

### 6.7 費用を左右する要因

下げる: Gumbel で平均シミュレーション数を150以下に／playout cap randomization の高速局比率を上げる／小ネット世代を長くして大ネットは蒸留＋短期継続／鏡映増強で必要局数を減らす／布石の DAG 合流で布石部分の推論を3〜5割削減。

上げる: 入玉・千日手ルールによる平均手数の増加／ホスト回線不良による GPU 遊休／学習ノードの待ち時間（自己対局が学習より速いと学習ノードが律速。逆なら GPU が遊ぶ）。学習ノードと自己対局プールの比率はダッシュボードで常時監視し、自動調整する。

### 6.8 工程

1. `libra-sim` と厳密性テスト、ルール確定（1〜1.5か月）。この間 GPU 費用はほぼゼロ。
2. 小ネットで統合自己対局とリーグの骨組み（段階 S、1か月）。
3. スケールアップ（段階 A→B、2〜3か月）。
4. 玉配置表の確定、分散対局系、USI 拡張エンジンと WASM ビルド、公開（1か月）。

### 7.2 ライセンス選択

| 対象 | ライセンス | 理由 |
|---|---|---|
| コード | Apache-2.0 | 特許条項付きで商用・研究とも取り込みやすい。GPLv3 のプロジェクトへの一方向の取り込みも可能 |
| 文書・図 | CC BY 4.0 | 転載・翻訳を許す |
| 自己対局棋譜・学習データ | CC0 1.0 | 自作 AI が生成したデータで第三者権利なし。再配布の摩擦を最小に |
| モデル重み | Apache-2.0 ＋ モデルカード | 重みの著作物性は国により曖昧なので、明示的な許諾文を付けておく |
| 玉配置表 JSON | CC0 1.0 | 事実データ |

代替案: コードを GPL-3.0 にすれば GPL の将棋エンジンからコードを流用できるが、下流の利用者に copyleft を強いる。「後続開発者が使いやすい」を優先するなら Apache-2.0。この計画書はゼロから書く前提なので流用の必要はない。

### 7.3 依存物のライセンス注意

| 依存物 | ライセンス | 注意 |
|---|---|---|
| PyTorch, NumPy, pybind11 | BSD 系 | 問題なし |
| Ray | Apache-2.0 | 問題なし |
| ONNX Runtime | MIT | 配布用推論バックエンドとして安全 |
| CUDA Toolkit, cuDNN, TensorRT | NVIDIA 独自ライセンス | ライブラリ本体をリポジトリや Releases に同梱しない。Dockerfile は NGC イメージ（nvcr.io）を取得する形にし、NVIDIA Deep Learning Container License に従う。TensorRT を使わない ONNX Runtime 経路を必ず残す |
| Redis 7.4 以降 | RSALv2/SSPL（8 系は AGPL も選択可） | 使わず Valkey（BSD-3）にする |
| KataGo | MIT | コード・手法を参考にしてよい。流用時は著作権表示を NOTICE に |
| Lc0, dlshogi, やねうら王, Apery, Stockfish | GPL-3.0 | Apache-2.0 で公開するならコードを一行も流用しない。手法・論文の参照は自由。クリーンルーム方針を CONTRIBUTING に明記 |
| fuseki-shogi-web（自作、GPL-3.0） | GPL-3.0 | 自身の著作物なので再許諾は可能だが、本計画では流用しない |
| vast.ai CLI/SDK | 公開リポジトリのライセンスを確認して LICENSES/ に収録 | API キーは絶対にコミットしない |
| 布石将棋のルール文（shogitter） | ルール自体は著作物でないが、条文の文章表現には著作権がある | ルール仕様は自分の言葉で書き直し、出典を明記 |

### 7.4 混入させてはいけないもの

- GPL エンジンのコード断片（合法手生成、評価関数、探索ルーチン、定跡）
- 第三者の棋譜（人間の対局、他エンジンの棋譜）。Libra は自己対局のみで学習するのでそもそも不要。評価用に外部エンジンと対局させる場合、その棋譜の公開可否は相手エンジンの利用条件を確認する
- NVIDIA のバイナリ（TensorRT の .so、.engine ファイルは環境依存でもあり配布しない）
- vast.ai の API キー、SSH 鍵、ホストの IP

### 7.5 大容量ファイルの配布

- GitHub 本体: ファイル 100 MB 上限。Git LFS は無料枠が小さく帯域課金があるので使わない。
- モデル重み: GitHub Releases（1ファイル 2 GB まで）と Hugging Face Hub の両方に置く。Releases には最終版のみ、世代ごとの中間重みは HF Hub。
- データセット（棋譜 30〜180 GB、学習データ 2〜11 TB）: Hugging Face Hub のデータセットとして分割公開。`data/` にはマニフェスト（ファイル名、SHA-256、サイズ、生成世代）と取得スクリプトのみ。
- Docker イメージ: GHCR に digest 固定で公開し、runbook にタグと digest を記録。

### 7.6 名称

「Libra」は一般名詞で、過去に Meta（当時 Facebook）の暗号資産名にも使われた。商標上の衝突を避け、検索性を上げるため、リポジトリ・パッケージ・実行ファイルは `LibraShogi` / `librashogi` とする。GitHub、PyPI、npm、ドメインの空きを公開前に確認する。

### 7.7 貢献の受け入れ

- DCO（Developer Certificate of Origin）の sign-off を必須にする。CLA より摩擦が小さい。
- 将来の再許諾（例: Apache-2.0 → 別ライセンス）は全貢献者の同意が要ることを README に明記。
- 依存追加時はライセンス確認を PR テンプレートの必須項目にする。SPDX 識別子をヘッダに付ける。
