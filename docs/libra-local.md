# Libra 実行計画 — ローカル主体・vast.ai 月1万円・年内に v0.1 公開

- 対象マシン: RTX 5070 Ti（16 GB）／Ryzen 9 9950X3D（16コア32スレッド）／RAM 64 GB（WSL2 に 32 GB 割当）／Windows 11 + WSL2
- クラウド: vast.ai、上限 月1万円
- 目標: 2026年内に Libra v0.1 を公開する。tenbin-shogi-desktop 上での「既存の方策ネット（fuseki-shogi-ai）＋水匠5」との対局は、勝てればよいという位置づけの計測（相手の分析や相手専用の対策はしない）
- 参照: 「Libra — 天秤将棋 最強AI 開発計画書」（設計の本体。本書はその実行計画）
- 作成日: 2026-09-11。同日、ルール規定（大会規定に統一）、公開時期（v0.1）、相手の分析をしない方針を確定。作業は Claude Code で行う（別紙「Claude Code 用プロンプト」）

注記: tenbin-shogi-desktop と fuseki-shogi-web は公開リポジトリで、本書は desktop の README と `docs/usi-fuseki-extension.md`（布石 USI 拡張 仕様 v0、2026-09-08）を読んで書いている。fuseki-shogi-ai は GitHub 上では 404（非公開）なので、Claude Code はローカルの clone を読む。読むのは接続と起動に必要な範囲（`scripts/fuseki_usi_server.py` の起動方法とオプション）だけで、相手 AI の中身の分析はしない。

## 0. 目標と制約の整理

| 項目 | 内容 |
|---|---|
| 年内の到達目標 | Libra-L（自己対局のみで学習した 10M ネット）を USI 拡張エンジンとして desktop に組み込み、v0.1 として公開する |
| 計測（勝てればよい） | desktop の既定設定で、置く側・選ぶ側を交互にした 100 局マッチ。相手は玉配置と布石が fuseki-shogi-ai の方策ネット＋玉配置表、41 手目以降が水匠5。結果は先手・後手別に報告する。**相手の分析、相手専用の対策、相手を固定した学習はしない**。Libra は自己対局だけで作り、この相手には計測として当てるだけ |
| 長期目標 | 計画書どおり「天秤将棋の最強 AI」。年内目標はその途中のマイルストーン |
| ルール規定 | 41 手目以降はコンピュータ将棋の大会（CSA／世界コンピュータ将棋選手権）と同じ規定にする。詳細は §0.1 |
| 公開 | リポジトリは v0.1 まで非公開。v0.1（年内のマッチ報告と成果物一式）で公開する |
| 計算資源 | ローカル 1 台が主。vast.ai は月1万円（約 $65、為替次第）で 5090 なら約 180 GPU 時間＝ローカルの 25% 増し程度。計画はクラウドに依存させない |
| 開発上の制約 | ゼロから開発。既存の将棋 AI のコード・評価関数・棋譜は Libra の内部に一切使わない。水匠5 と既存方策ネットは「計測用の対戦相手」としてのみ使う（別プロセス、USI 経由）。学習の相手にもしない |
| 運用上の制約 | Windows Update などで突然再起動する。別作業のため GPU/CPU を空けたいことがある。→ いつでも停止・再開できること（§7） |

### 0.1 ルール規定（確定）

布石フェーズ（1〜40 手目）と 41 手目の裁定はルールページのとおり。41 手目以降の本将棋は、コンピュータ将棋の大会規定に合わせる。

| 項目 | 規定 | 備考 |
|---|---|---|
| 千日手 | 同一局面（盤・持ち駒・手番。手数は含めない）が 4 回目で成立、引き分け | 公開版と同じ |
| 連続王手の千日手 | 繰り返しの間ずっと王手をかけていた側の負け | 公開版と同じ |
| 入玉 | 入玉宣言法（27 点法）。宣言側の手番で、(1) 宣言側の玉が敵陣三段目以内、(2) 敵陣三段目以内の宣言側の駒（玉を除く）が 10 枚以上、(3) 敵陣三段目以内の駒と持ち駒の合計点が先手 28 点以上・後手 27 点以上（飛角と成駒の飛角 5 点、その他 1 点、玉 0 点）、(4) 宣言側の玉に王手がかかっていない、(5) 持ち時間が残っている。条件を満たさない宣言は宣言側の負け | 公開版の「合意による持将棋」は採らない。エンジンの `win` は宣言として受け、ハーネスが条件を検証する |
| 最大手数 | 256 手で引き分け | 手数の数え方は「41 手目を 1 手目として数える（本将棋フェーズ 256 手、通算 296 手）」を提案。通算 256 手にするかは要確認 |
| その他 | 打ち歩詰め・二歩・行き所のない駒は反則負け。詰みは手数上限より優先 | 標準どおり |

実装上の扱い:

- `libra-sim` はこの規定を唯一の正とし、`docs/rules.md` に条文として固定する。256 手と宣言法の条件は実装前に大会の最新規定文で照合する。
- 既存部品との差: 公開版（fuseki-shogi-web）は 320 手・合意持将棋、学習アリーナは千日手判定なし・256 手、デスクトップ GUI は千日手・手数上限・宣言法いずれも無し。**年内のマッチはハーネス側が本規定で裁定し、GUI は表示と手動対局に使う。** GUI に千日手・手数上限・宣言法の判定を足すのは tenbin-shogi-desktop 側の別作業（任意、§5 週 9〜12）。
- 公開版との差（320 手→256 手、合意持将棋→宣言法）は公開版を更新するかどうかの判断が別途要る。Libra 側は大会規定で固定して進める。

### 年内の結果の見方

- 本将棋フェーズで水匠5 と互角に指すことは、年内・この計算量では無理。Libra-L の 41 手目以降の実力は水匠5 に大きく劣る前提で計画する。
- 相手の分析や相手専用の対策をしないので、年内のマッチ結果は「自己対局だけで作った Libra-L の素の実力」の計測になる。負け越しが自然な結果であり、勝てれば上出来。
- 自己対局の設計そのものに含まれる要素で、結果的に効く可能性があるもの: 配置詰みと 41 手目の証明探索（後手番で即死を完全に避け、先手番で相手の見落としがあれば勝つ）、自前の玉配置表に基づく先後選択。これらは相手対策ではなく Libra の標準機能なので、そのまま使う。
- 年内に固定する指標: 100 局マッチの得点（先後別）、配置詰み・証明詰みの発生件数、玉配置ペアの分布、Libra-L の世代間 Elo と較正。これを v0.1 の基準値として公開し、以後の世代で追う。

## 1. ハードウェアの評価

| 部品 | できること | 制約 |
|---|---|---|
| RTX 5070 Ti | テンソル演算の実効値は RTX 4090 とほぼ同等（試算では 4〜7×10^13 FLOP/s。小さいネットほど利用率が下がる）。10〜30M ネットの学習と自己対局を 1 枚で兼ねられる。300M〜1B の**推論**（FP16/FP8）は余裕 | 自己対局と学習を時分割（自己対局 85%、学習 15%）。300M の学習は勾配チェックポイント込みでぎりぎり、1B の学習は不可。数百枚並列前提の分散設計（Ray、分散 MCGS）は不要 |
| Ryzen 9 9950X3D | シミュレータ・MCGS・df-pn・配置詰み探索に十分。同時進行 512 局程度を GPU に食わせ続けられる。水匠5 を対戦相手として回すのにも十分（8 スレッド × 2 局並列） | 小さいネットでは GPU より CPU 側が先に飽和しうる。プロファイルして確認 |
| RAM 64 GB（WSL2 に 32 GB 割当） | WSL 側の 32 GB のうち OS・シミュレータ・MCGS の置換表に 8〜10 GB を残すと、リプレイウィンドウは圧縮局面（約150 B/局面）で 1〜1.3×10^8 局面まで載る。Libra-L の L-S ならこの範囲で足りる | ウィンドウを広げたくなったら `.wslconfig` の `memory` を 48〜52 GB に上げる（Windows 側の常用に 12 GB 以上残す）か、ウィンドウを NVMe 上のメモリマップに逃がす |
| ストレージ | 棋譜は 300 B/局なので 3,000万局で約 9 GB。学習データは 120 B/局面で 3,000万局×150 ≈ 540 GB | 学習データを全部保持するなら 1 TB 以上の NVMe。ウィンドウ外は棋譜だけ残せば数十 GB で済む |

## 2. 計算量から見た到達可能範囲

計画書の計算モデル（1局面の推論 ≈ 2×パラメータ数×90×1.15 FLOP、1局150手、上乗せ×1.35）を、5070 Ti の実効 7×10^13 FLOP/s、自己対局への割当 85% で割ると:

| 計画書の段階 | 自己対局 FLOP | このマシン 1 台での所要 |
|---|---|---|
| S 検証（30M×2×10^7局） | 5.0×10^21 | 約2.7年 |
| A 最小実用 | 5.5×10^22 | 約29年 |
| B 推奨 | 3.6×10^23 | 約190年 |
| C 上限 | 2.9×10^24 | 約1,500年 |

参考: AlphaZero が将棋で elmo を超えた学習（約2,400万局、20ブロック256フィルタ、800シミュレーション）をそのまま再現すると約1.1×10^22 FLOP、このマシンで約6年。KataGo・Gumbel 系の効率化を全部入れて 1/20〜1/50 になれば数か月に縮む可能性はあるが保証はない。本将棋をゼロから学習する有志プロジェクト（AobaZero）が多数のボランティア GPU で年単位を要していることも目安になる。

## 3. ローカル向けに縮めた構成「Libra-L」

### 3.1 何を残し、何を縮め、何を捨てるか

| 区分 | 項目 |
|---|---|
| 残す | `libra-sim`（厳密シミュレータ、perft、ルールテスト）／単一ネットの統合自己対局／布石の MCGS と Zobrist 合流／配置詰み・41手目の証明探索／df-pn（ノード上限を小さく）／補助ヘッド（V̂41、次手予測）／鏡映増強／玉配置表の作り方（剪定→探索値→バンディット検証） |
| 縮める | ネット規模 10M（L-S）または 30M（L-M）／平均シミュレーション 50〜100（Gumbel、全読み25%＋速読み75%）／リーグは搾取者 1 体を 10% の計算で定期的に回すだけ／検証対局は 100 ペア×1,000〜2,000 局 |
| 捨てる | 300M・1B ネット／蒸留ラダー／Reanalyze／Ray・分散 MCGS・対局時の多 GPU 並列 |
| 年内に間に合わせる順序 | シミュレータ → 統合自己対局 → 配置詰み・41 手目の証明探索を布石終端に接続 → 玉配置表 v0（自己対局由来） → USI 拡張エンジン → 計測マッチ |

### 3.2 二つの構成と所要期間

| 構成 | ネット | 平均sim | 1局の FLOP | 理想値（局/日） | 現実値（×0.5、局/日） | 1,000万局 | 3,000万局 |
|---|---|---|---|---|---|---|---|
| L-S | 10M | 50 | 1.9×10^13 | 約16万 | 約8万 | 約4か月 | 約13か月 |
| L-M | 30M | 100 | 1.1×10^14 | 約4万 | 約2万 | 約17か月 | 約4年 |

年内は L-S 一本。10月初旬に回し始めれば 12 月末までに 500 万〜800 万局。L-M への拡張は年明け以降。学習側の負担は小さく（L-S で 1,000万局を 3 パスしても GPU 換算 8 日）、自己対局が律速。玉配置表の検証対局は 100 ペア×1,000 局で約 4 日。

### 3.3 実装上の変更点

- 自己対局と学習を同一プロセス群で時分割。学習は「新規 N 局ごとにミニバッチ M 回」の固定比率。
- 推論は TensorRT（WSL2 で可）または ONNX Runtime CUDA EP。ネットが小さいので FP16 で十分。バッチは同時進行 256〜512 局から集める。
- MCGS の置換表とリプレイはプロセス内メモリ＋ NVMe 上のチャンクファイル。外部 KV ストアは使わない。
- 対局用エンジンは単一プロセス・マルチスレッド。

## 4. 計測マッチの扱い

相手の分析はしないが、計測としてのマッチは行う。条件を固定して、世代ごとに同じ物差しで測る。

| 項目 | 内容 |
|---|---|
| 相手 | fuseki-shogi-ai の `scripts/fuseki_usi_server.py`（布石。`Normal_Engine` でやねうら王へ中継）＋ desktop が自動で入れるやねうら王 V9.00（NNUE_halfkp_256x2_32_32、AVX2）と水匠5 の `nn.bin`（41 手目以降）。コミットハッシュ・評価ファイルのハッシュ・スレッド数・持ち時間を報告書に固定 |
| 形式 | 置く側・選ぶ側を交互に 100 局。ハーネスが両エンジンを USI で駆動し、`choose` はハーネスが各エンジンの 2 手目後の `winrate` で決める。終局判定はハーネスが §0.1 の大会規定で行う |
| Libra 側 | Libra-L の最新世代。玉配置は自前の `scale.json`（置く側は釣り合い集合から一様、選ぶ側は 2 手目後の局面の `winrate` の符号）。布石は MCGS＋証明探索、本将棋は MCTS＋df-pn。相手に応じた設定変更はしない |
| 頻度 | 10 月中旬に 20 局で基準値、以後 2 週間に 1 回 20 局、12 月に 100 局 |
| 記録 | 棋譜 JSONL、先後別の得点、配置詰み・証明詰みの件数、終局理由の内訳（詰み・千日手・宣言・256 手・反則） |
| 使わないこと | 水匠5 の評価値・読み筋・棋譜を Libra の学習信号にしない。既存方策ネットの重みを初期値にしない。相手の玉配置表を読まない。相手を固定した学習をしない |

引き分けの扱い: 千日手・256 手・宣言の引き分けは 0.5 点。後手番では引き分けが多く出る可能性があり、それも Libra の性質として記録する。

### 6.2 desktop との接続（布石 USI 拡張 仕様 v0 に準拠）

desktop は Tauri v2 製で、エンジンは USI で起動される。布石中の語彙は desktop の `docs/usi-fuseki-extension.md` が定めており、Libra はこれにそのまま従う。

| 項目 | 仕様 v0 | Libra の実装 |
|---|---|---|
| 布石の局面 | `position fuseki` ／ `position fuseki moves K*5i K*5a P*7g ...`。打ち手は `X*sq`、駒の文字は手番に関わらず大文字 | そのまま。天秤将棋では 1・2 手目が玉打ち |
| 先後の選択 | `choose:sente` / `choose:gote` はエンジンに**送らない**。送られても読み飛ばす | 読み飛ばす。選ぶ側の判断は 2 手目後の局面に `go` を受けて `winrate`（手番＝先手の勝率）を返すことで表現し、選択そのものはハーネス（または GUI）が行う |
| 41 手目の裁定 | 40 手完了時点で手番側が相手玉を取れる局面では `go` に `bestmove win` を返す（探索しない） | そのまま。加えて 39 手目直後に遮断不能が確定した局面も内部では終局として扱う |
| 本将棋 | `position sfen <41手目のSFEN> moves ...`。素の USI | そのまま。持ち駒なしの SFEN を受ける |
| 思考 | `go infinite` / `go nodes N` / `go movetime T` / `stop` | すべて対応。`go` の持ち時間語も受ける |
| 出力 | `info depth 1 multipv k score cp X winrate W pv M`、`info string phase fuseki|normal ply N method <名>`。`winrate` は手番側の勝率 0..1、`score cp` は勝率を S=435・offset +34cp の逆ロジスティックで擬似 cp にしたもの | 布石中は候補ごとに `winrate` と擬似 cp を出す。換算は GUI の `src/usi/parse.ts` の `cpToWinrate` と厳密に逆関数になるよう実装し、テストで固定する。`method` は `mcgs` を名乗る |
| オプション | `MultiPV` は布石中も有効。既存 AI の `Fuseki_*`・`Normal_*` は既存 AI 固有 | `MultiPV`、`Threads`、`DNN_Model`（ONNX パス）、`DNN_Batch_Size`、`Sims_Fuseki`、`Sims_Normal`、`Scale_Table`（`scale.json` パス）。既存 AI 固有のオプションは持たない |
| GPU エンジン扱い | 申告に `DNN_` の項目があると GUI は GPU エンジンとして扱う（同時に 1 本、準備の待ち時間が長い、エンジン同士の対局では先後で 1 本を共用、勝率目盛りは `Eval_Coef` から読む） | `DNN_Model` を持つので GPU 扱いになる。`Eval_Coef` の扱いは GUI の実装を確認して合わせる（`winrate` を常に出すので、GUI が `winrate` を優先する限り目盛りの問題は出ない） |
| 登録 | 「実行ファイルを選んで追加」→ `usi` の申告から設定画面が作られる。「使える局面」で「布石にも対応」を選ぶ | Releases の zip を展開し、`libra.exe` を登録。README に手順を書く |

要確認（Claude Code が GUI のコードで確かめる）: GUI が `Fuseki_Mode=tenbin` のようなオプションを送るか／布石中の `go` に持ち時間語が付くか／`bestmove` の後に GUI が合法性を wasm で検証するか／`Eval_Coef` を宣言しない DNN 系エンジンの勝率目盛りをどう扱うか。

その他:

- GUI の布石の合法性検査は dlshogi 由来の wasm（GPL-3.0）で行われる。Libra はこのコードを使わず自前で実装するが、合法手集合が一致することを黒箱テストで確かめる（ランダム局面で GUI 側の wasm と `libra-sim` の合法手を突き合わせる。GPL コードはテストの相手としてだけ動かす）。
- GUI には千日手・手数上限・宣言法の判定が無いので、計測マッチは GUI ではなく自前のハーネスが両エンジンを USI で駆動し、§0.1 で裁定する。GUI は表示・手動対局・検討に使う。
- ビルドは公開前は WSL 内の mingw-w64 クロスビルド、公開後は GitHub Actions の `windows-latest`。開発中は desktop に `wsl.exe -d Ubuntu -- /path/to/libra usi` を登録して暫定的に動かせる。
- 依存ライブラリを `libra.exe` に静的リンクし、ONNX Runtime の DLL だけ同梱する。TensorRT は同梱しない。desktop 同梱の dlshogi が DirectML で動いている前例に倣い、CUDA が無い環境向けに ONNX Runtime の DirectML EP も検討する。

### 6.3 リポジトリの形（計画書 §7 と同じ）

`LibraShogi/` monorepo、コード Apache-2.0、文書 CC BY 4.0、自己対局データ CC0、重み Apache-2.0。GPL の将棋エンジンからのコード流用ゼロ。水匠5・やねうら王は別プロセスで動かすだけなので GPL は伝播しない。

公開は v0.1 で行う。それまでの注意:

- 非公開リポジトリでは GitHub Actions の無料枠が限られ、Windows ランナーは消費が 2 倍。公開までは CI を Linux のテストだけにし、`libra.exe` は WSL 内で mingw-w64 クロスビルドする（ONNX Runtime の Windows 版バイナリをリンク）。公開後に Windows ランナーへ切り替える。
- 公開前に git 履歴を点検する（秘密情報、外部からコピーしたファイルが無いか）。疑わしければ履歴を捨てて squash した状態で公開する。
- Hugging Face 側のデータセット・モデルも v0.1 まで private にし、公開時に一括で public へ切り替える。
- v0.1 のタグ時点で LICENSE・NOTICE・LICENSES/・モデルカード・データシートが揃っていることを公開の条件にする。

## 7. 停止・再開の設計

### 7.1 原則

- **状態はすべてディスク上の 1 ディレクトリ**（`~/libra-run/<run-id>/`）: `state.json`（世代、ステップ数、乱数状態）、`checkpoints/`（10 分ごと、原子的に書き換え）、`replay/`（100 局単位の追記チャンク＋索引）、`games/`（棋譜 JSONL）、`PAUSE` フラグ。
- **`libra run` は冪等**: 起動時に `state.json` から再開する。実行中だった局は捨てる（損失は最大で同時進行分＋チェックポイント間隔 10 分）。
- **強制終了に耐える**: チャンクは書き終えてから索引に登録する。索引に無いチャンクは起動時に検証して回収か破棄。

### 7.2 コマンド

| コマンド | 動作 |
|---|---|
| `libra run [--resume]` | 前回状態から再開。無ければ新規 |
| `libra pause` | `PAUSE` フラグを置く。ワーカーは現在のバッチを終えて（10 秒以内）GPU メモリを解放し待機。学習も止まる |
| `libra resume` | フラグを消す。数秒で復帰 |
| `libra stop` | 正常終了（30 秒以内にフラッシュして exit） |
| `libra throttle --games N` | 同時進行局数を減らして負荷を落とす（軽い作業向け）。重い作業は `pause` |
| `libra status` | 世代、局/日、Elo、ETA、GPU/CPU 使用率、直近の再起動履歴 |

Windows 側にはデスクトップのバッチファイル `libra-pause.bat` / `libra-resume.bat` / `libra-status.bat`（中身は `wsl.exe -d Ubuntu -- libra pause` など）を置く。

### 7.3 Windows Update で再起動しても続くようにする

1. 自動ログオンを有効にする（`netplwiz`）。
2. タスクスケジューラに「ログオン時」のタスクを登録: `wsl.exe -d Ubuntu -- /home/<user>/librashogi/bin/libra run --resume`。「非表示」「失敗時 1 分後に再起動」「最上位の特権なし」。
3. `wsl.exe` をフォアグラウンドで持ち続けるので WSL の VM がアイドル終了しない。
4. 再起動後の損失は最大 10 分。Windows Update は「アクティブ時間」を広めに設定して深夜以外の再起動を避ける。
5. 停電・クラッシュに備え、`checkpoints/` の最新 2 世代を Windows 側または外部ストレージへ 1 日 1 回コピー。

### 7.4 別作業でリソースを空けるとき

- GPU を使う作業（ゲーム、別の学習、動画処理）: `libra-pause.bat`。終わったら `libra-resume.bat`。
- CPU だけ使う作業: `libra throttle --games 64`。ワーカーは `nice 10` で動くので通常作業は妨げない。
- 数日止めても再開時のコストはゼロ。止めた日数だけ到達が遅れるだけ。

## 8. 運用

### 8.1 電気代と熱

- 平均消費電力は GPU 300 W ＋ CPU 約 100 W ＋その他 50 W で約 450 W。24 時間で 10.8 kWh、31 円/kWh なら 1 日約 335 円、月約 1 万円、年約 12 万円。
- GPU の電力上限を 250 W に下げると性能低下は数% で、月約 9,000 円。長期運転ではこちらを推奨。
- 連続高負荷で数か月回すなら、ケースのエアフローと定期的な清掃が必要。

### 8.2 WSL2 での注意

- `.wslconfig` で `memory` と `swap` を明示。現在の 32 GB 割当で L-S は回るが、ウィンドウを 10^8 局面より広げるなら 48〜52 GB に上げる。
- データは ext4 側（WSL 内）に置く。`/mnt/c` 経由の I/O は遅い。
- WSL2 の systemd を有効にし、ログ回転と監視を service 化。ワーカー本体は §7.3 のタスクスケジューラ経由で起動する（VM を生かし続けるため）。
- CUDA on WSL のオーバーヘッドは数%〜10%。年内は WSL のままでよい。

## 9. vast.ai 月1万円の使い方

月1万円は 5090 の割込可能インスタンスで約 180 GPU 時間（4090 なら約 250 時間）。ローカルの 25〜35% 増しにしかならないので、常時併用ではなく「並列性が効く短期作業」に使う。

| 時期 | 使い方 | 目安 |
|---|---|---|
| 9〜10 月 | 使わない（開発期） | 0 円 |
| 11 月 | ハイパーパラメータの並列比較（8 台 × 1 日の短期実行）、または玉配置表の検証対局（ペアごとに独立なので並列が効く） | 1 万円 |
| 12 月 | 100 局計測の並列実行（水匠5 は CPU なので CPU の多いインスタンスを選ぶ）と、余れば自己対局ワーカーの追加 | 1 万円 |

ワーカーは同じ Docker イメージ・同じ状態ディレクトリ形式で動かし、`replay/` のチャンクをオブジェクトストレージ経由で同期する。これで「ローカルで回している run に、クラウドのワーカーが一時的に加わる」形になる。前払いのクレジット制なので上限管理は容易。使わなくても計画は成立する。
