# ネットの入力に「ピン」「詰めろ」を足す案の検討（2026-09-24）

ユーザーの依頼「docs/two-piece-table-2026-09-24.md の §4（表より根拠のある近い案＝入力を足す）に導入価値があるか検討する」への答え。**検討だけで、実装・設定・学習ランには何も触っていない。**

## 結論

**今は入れない方がよい。すすめない。**

1. **ピンはネットがすでに自力で分かっている。** 公開した v0.2 の重みの中を調べると、「この駒はピンされているか」を8層のうち4層目でほぼ正確に読み出せた（§3）。入力に渡しても、ネットにとって新しい情報にならない。
2. **1手詰めも詰めろ（相手に1手詰めの狙いがある）も、ネットの判断にもう入っている。** 詰めろは中からの読み出しが 0.68 と弱めだった（§3.2）ので、ユーザーの指示で詰めろだけ追加で測った（§3.3）。詰めろの局面で価値（勝ち負けの予測）に偏りは無く、詰めろの印を足しても結果の予測は良くならなかった。方策（次の一手の候補）は、受ける手に確率の約 89% を置いていた。計算は1局面 約8〜10マイクロ秒と軽いが、入れて得るものが無い。
3. **費用は小さくない。** 入力の形が変わると、学習中の ls、過去の重みすべて（計測の相手）、エンジン、サイト、デスクトップの配布物に手が入り、比べる計測には ls・lx の停止が要る（§4）。
4. KataGo が入力を足して学習を 1.55 倍速めた例（§2）は、**小さな畳み込みのネットの学習の出だし（全体の約 1 割の時点）**での値で、足した量には畳み込みでは計算しにくいもの（シチョウなど）が含まれていた。Libra は Transformer で、480 万局を過ぎており、条件が違う。

ピン・1手詰め・詰めろのどれも、入力に足さない。

## 1. 用語

| 用語 | 意味 |
|---|---|
| ピン | 動くと自分の玉が相手の飛・角・香に取られるので動けない駒 |
| 詰めろ | 何もしなければ次に詰まされる状態。ここでは「相手に1手詰めがある」で数えた |
| 入力（特徴） | ネットに渡す局面の説明。今は81マスそれぞれの32個の数（駒の種類と持ち主、利きの数など）と、全体の32個の数 |
| 線形の読み出し（プローブ） | ネットの途中の層の中身から、ある量を足し算と重みだけで当てられるかを試す方法。当てられれば、ネットはその量をもう中で計算している |
| AP（平均適合率） | めったに起きないもの（ピンは駒の約1%）を当てる成績。1.0 が満点、でたらめならその起きる割合（約0.01）。AUC より厳しい |

## 2. 採用の経緯と一次資料

### 2.1 経緯

- 計画書（docs/libra-design.md §3.2）の入力は「81マストークン（駒種・所有・利き数・ピン）」。今の入力（`libra-sim/src/encoding.cpp` の `write_features`）には**ピンが無い**。
- 外した理由の記録は docs/decisions.md・docs/protocol.md §4 に無い（**記録なし**）。公開リポジトリの履歴は 2026-09-20 から（それより前のコミットは公開時にまとめた）なので、`git log -S` でも追えない。手元の過去の会話（`~/.claude/projects`）はこのセッションからは読めない（**未確認**）。
- 計画書は「ピン」を足す理由を書いていない（出典なし）。

### 2.2 読んだ資料

| 資料 | 読んだ範囲 | 分かったこと |
|---|---|---|
| Wu 2019「Accelerating Self-Play Learning in Go」（KataGo、arXiv:1902.10565） | §4.2、§5.2、表2、付録 A.1 | 足した入力は呼吸点・コミの偶奇・パスしても生きる地・シチョウ。**削った実験（NoGoFeat）は入力のほかにパスの扱いの小さな工夫も一緒に外している**。20ブロック×256 のネットで約2日（本番は19日）、2.5G クエリの時点の Elo で比べて 1.55 倍。論文は「学習を目に見えて速めるが、全体の改善の一部にすぎない」とし、コミの偶奇は「ネットが自力で学ぶのはとても難しい」と書く。**後半の学習でも効くかは測っていない** |
| McGrath ほか 2022「Acquisition of Chess Knowledge in AlphaZero」（arXiv:2111.09259） | 方法の節（層ごとの疎な線形の読み出し、10万局面で学習し3万局面で試す）と結果 | AlphaZero のネットの中から、王手・駒を取れる・脅威・**1手で詰ませる狙い（has_mate_threat）**が読み出せた。王手や脅威は最初の数層で読み出せるようになり、「1手先を読む計算がネットの中で行われている」と書く。ピンそのものの概念は調べていない |
| Monroe・Chalmers 2024「Mastering Chess with a Transformer Model」（Lc0 の Transformer、arXiv:2409.12272） | 付録 A-A の入力、§1 | 入力は駒の位置と過去の局面だけで、利きやピンのような手作りの量は入れていない。「畳み込みは遠くの関係が苦手、Transformer の注意はそれを解く」 |
| 山岡 2024-12「【dlshogi】入玉特徴量」とその2（dlshogi の作者の開発日記） | 各記事の本文 | 将棋で「ネットが計算しにくい量」を入力に足した近い例。入玉宣言の点数を足すと、**入玉の局面の価値の正解率は 95.4% → 96.5% と少し上がったが、一般の局面では変わらず、対局の強さでは足さない版がいちばん上だった**（宣言勝ちの局が出なかったので強さの結論は出ていない、と著者） |

Libra の入力にはすでに、利きの数（遠くの駒の利きも盤の駒で止まる形で数える）、王手、入玉の点数と枚数がある。KataGo のシチョウや dlshogi の入玉の点数に当たる「計算しにくい量」は、一部はもう入っている。

## 3. v0.2 のネットはピンと詰めろを分かっているか（実測）

McGrath ほか 2022 の方法をそのまま使った（層ごとの線形の読み出し）。**変えた点**: 疎な回帰ではなく L2 のロジスティック回帰（C = 0.1、陽性と陰性の重みを釣り合わせる）。試す局面は対局単位で 1/4 を分けた（同じ対局の局面が学習と試しの両方に入らないように）。

- 重み: GitHub Release v0.2 の `libra-v0.2.pt`（step 317,975。d 320・8層、1,023万パラメータ）。
- 局面: 同じ Release の自己対局の標本（172,600 局）から、41手目より後の本将棋の局面を無作為に取った。
- ピンの正解: 玉から8方向にたどって作った。駒を1枚ずつ盤から持ち駒に移して「玉に王手が掛かるか」を libra-sim に判定させた答えと、**5万7,204 駒ですべて一致**（食い違い 0）。
- 詰めろの正解: libra-sim の合法手を1手ずつ指して終局（手番側の勝ち）になるかで1手詰めを判定。詰めろは、王手でない局面で手番を相手に替えて、相手に1手詰めがあるかで判定。

### 3.1 ピン（2,000 局・16,000 局面、玉以外の駒 約24万枚）

- 本将棋の局面の **28.8%** にピンがある（手番側の駒 14.9%、相手の駒 16.2%）。盤上の駒のうちピンされているのは約 1.1%。
- 読み出しの成績（試しの局面。AP は 1.0 が満点、でたらめなら約 0.011）:

| 読み出す場所 | 手番側の駒のピン AP | 相手の駒のピン AP |
|---|---|---|
| 入力そのもの（そのマスの32個の数） | 0.13 | 0.12 |
| 1層目の後 | 0.79 | 0.76 |
| 2層目の後 | 0.93 | 0.94 |
| **4層目の後** | **0.98** | **0.99** |
| 8層目の後（最後） | 0.97 | 0.97 |

入力だけからはほとんど当たらない（ピンは入力にない）のに、2層目で 0.93、4層目で 0.98 まで上がる。**ネットはピンを前半の層で自分で計算している。** 入力にピンを足すと、この前半の層の仕事が少し減るだけになる見込み。

### 3.2 詰めろ（3,000 局・12,000 局面、全体のトークンから読み出す）

価値（勝ち負けの予測）は全体のトークン（81マスとは別の1個）から出すので、そこから読み出した。王手の局面は詰めろの判定から除いた（9,912 局面）。

- 本将棋の局面の 2.7% で手番側に1手詰めがあり、王手でない局面の 3.6% で詰めろを掛けられている。
- 読み出しの成績（試しの局面。AP は 1.0 が満点、でたらめなら陽性率の約 0.02〜0.04）:

| 読み出す場所 | 手番側に1手詰めがある AP | 詰めろを掛けられている AP |
|---|---|---|
| 入力そのもの（81マス × 32 と全体 32 をすべて） | 0.11 | 0.09 |
| 2層目の後 | 0.56 | 0.30 |
| 4層目の後 | 0.71 | 0.67 |
| **8層目の後（最後。ここから価値を出す）** | **0.94** | **0.68** |

1手詰めは最後の層でほぼ正確に読み出せる。詰めろは 0.68 で、陽性率 0.036 に比べればよく当たっているが、ピン（0.98）や1手詰め（0.94）ほどではない。**ネットが中で完全には計算できていない量で、入力に足す候補になるのは今回調べた中では詰めろだけ。**

そこで、入れる前に確かめることを2つ測った（§3.3）。

### 3.3 詰めろの追加の計測（2026-09-24、ユーザーの指示「詰めろだけ計測して結論を出す」）

**(a) 詰めろの局面で、ネットの予測が外れやすいか。** 同じ標本の 6,000 局から、本将棋で王手でない局面 19,774 を取った（詰めろ 821）。価値 v は WDL の勝ち − 負け、結果 z は手番側から見た勝ち +1・引き分け 0・負け −1。

| 局面 | 数 | 予測の平均 | 結果の平均 | 偏り（予測 − 結果） | 二乗誤差 |
|---|---|---|---|---|---|
| 詰めろなし | 18,953 | +0.087 | +0.104 | −0.017 | 0.459 |
| 詰めろあり | 821 | −0.178 | −0.177 | **−0.002** | 0.319 |
| 詰めろあり・自分に1手詰めなし | 756 | −0.279 | −0.278 | −0.002 | 0.347 |

- **偏りは無い**。詰めろを掛けられた局面を、ネットは平均でちょうど結果どおりに不利と見ている。
- 二乗誤差を、同じ手数の分布にそろえた詰めろなしの局面（0.366）と比べると小さく、同じ確信度（予測の絶対値）にそろえた局面（0.279）と比べるとやや大きい。確信度が同じなら詰めろの局面の方が結果がぶれやすいが、下の検定のとおり、詰めろの印を知っても当て直せるぶれではない。
- **詰めろの印を足して結果を当て直せるか**: ネットの予測（勝ちと負けの対数比）だけで結果（引き分けを除く勝ち負け）を当てるロジスティック回帰と、詰めろの印・印と予測の積・自分の1手詰めの印を足したものを、対局単位で 1/3 を分けて比べた。試しの対数損失は 0.35054 → 0.35036、改善 0.00017（95% 区間 −0.00005〜+0.00047、局単位のブートストラップ 1,000 回）で、**0 と区別できない**。詰めろの局面（283）だけでも 0.3065 → 0.3027。
- 方策: 詰めろの局面で、受ける手（指した後に相手の1手詰めが消える手か、その手で勝つ手）は合法手の 11.3% だが、**方策は受ける手に確率の 88.9% を置き、1番手が受ける手である割合は 92.1%**。対局で実際に指した手は 94.3% が受ける手（受けの無い詰めろ＝必至は 0 局面）。

**(b) 計算の重さ。** 詰めろの判定を C++ で素直に書いた（手番を相手に替え、王手になる手だけを指して相手に合法手が無いかを見る）。クラウドの CPU の1スレッドで、自己対局の局面 467,513（王手でない 385,497）: **詰めろの判定 1局面 8.1〜9.9 µs**、今の特徴の書き出し 1.3〜1.6 µs。手元の ls は GPU 待ちが長く、12 スレッドなら1回の評価（約 27 ms）あたり 512 × 約 9 µs ÷ 12 ≈ 0.4 ms、約 1.5% の見込み（手元では未計測）。重さは入れない理由にならない。

**(a) と (b) の結論**: ネットは詰めろを価値でも方策でもすでに扱えている。線形の読み出しが 0.68 だったのは、全体のトークン1個から足し算だけで取り出すのが難しい形で持っているためと考えられる（推測）。入力に足しても強くなる見込みは無い。

### 3.4 この計測で言えないこと

- 読み出せることは、ネットがその量を**判断に使っている**ことまでは示さない（McGrath ほか も同じ注意を書いている）。ただ、中で計算できている量を入力に足しても、ネットが新しく知ることは無い。
- 調べたのは v0.2（step 317,975）と、その前後1時間の自己対局の標本。今の ls（step 42 万台）は未確認だが、学習が進んで読み出せなくなることは考えにくい。
- 布石（40手目まで）は調べていない。布石では駒が動かないので、ピンは41手目から効く。

## 4. 入れるときの費用（入れない判断の材料）

| 対象 | 何が要るか |
|---|---|
| libra-sim | `write_features` にピンを足す（計算は安い。合法手生成にピンの候補を探す処理がすでにある） |
| 学習中の ls | 入力の形が変わる。新しい入力の重みを 0 で始めれば今の重みから続けられ、足した直後は出力が変わらない。**リプレイの窓は棋譜（指し手）から特徴を作り直すので、そのまま使える**。CLAUDE.md の「ネットの形を変えるなら新しい run-id」に当たるかはユーザーの判断 |
| 過去の重みすべて | 最強比・基準比・固定の参照・v0.1・v0.2・搾取者の凍結相手（main.pt）は、新しい入力を読めない。全部を「足した入力の重みを 0 にした形」に書き換える変換が要る（出力は変わらない） |
| 比べる計測 | `libra abtest` は学習側の設定だけを変える作りなので、入力を切り替える腕を足す改修が要る。回す間（約1時間）は ls・lx の停止と起動をお願いする。学習データに関わる変更なので、その日はほかの変更を入れない（CLAUDE.md 11） |
| エンジン（libra / libra.exe） | 定数から作っているので作り直すだけ。ただし重みとエンジンは組で配る必要があり、古い zip に新しい重みを入れると動かない |
| サイト | `src/engine/libra/net.ts` の入力の大きさ、ルールと探索の WASM、一致試験の局面集、fp16 の変換を次の重みの差し替えのときに合わせて直す |
| デスクトップ | zip の入れ替えと、GUI でのエンジンの登録し直し（利用者の操作） |
| vast.ai のワーカー | 使う時期には作り直しが要る |

形を変えずに入れる手もある。1マスの32個のうち最後の2個（自陣・敵陣の印）は手番側から見たマスの位置だけで決まり、ネットには別にマスの位置の重み（`pos_embed`）があるので、その2個の重みを位置の重みに畳み込めば同じ出力のまま空けられる。全体の32個のうち3個（29〜31）も空いている。こうすると配布物の入力の大きさは変わらないが、**古いエンジンと新しい重みを組み合わせても誤りが出ずに間違った値を読む**ので、取り違えに気付けない危うさが増える。

## 5. それでも入力を足すなら

- 詰めろは §3.3 で測り、足さないと決めた。
- ほかの量も、**先に今のネットで線形の読み出しをして、読み出せないものに絞る**（§3 と同じ手順。CPU で30分ほど、ls・lx の停止は要らない）。読み出せない量なら、KataGo の「ネットが自力で計算しにくい量」に当たる。
- 玉の逃げ道の数（玉の周り8マスの利きの有無）は、入力にある利きの数から1層で出せる形なので、読み出せる見込みが高い（未確認）。
- 布石については、計画書 §3.2 の補助の学習目標「後手玉に当たる利き本数・遮断可否」も未実装で、41手目の裁定に直接効く量なので、入力よりこちらの方が候補になる（出典なし、未確認）。
